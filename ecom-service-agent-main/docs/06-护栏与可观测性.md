# 06 · 护栏、兜底与可观测性

对应代码：`app/agent/guardrails.py`、`app/agent/observability.py`、`tools/errors.py`

## 1. 四道护栏

| 护栏 | 触发时机 | 行为 |
|---|---|---|
| **越界检查** `check_boundary` | 父图 `preprocess` 节点 | 判定问题是否在电商客服能力范围内；越界直接阻断并建议转人工，不进子图 |
| **幻觉检测** `detect_hallucination` | 回复生成之后 | LLM-as-Judge 对照工具返回数据，核查订单号 / 金额 / 时效 / 政策引用是否杜撰 |
| **自纠错** `self_correct` | 检测到幻觉时 | 把具体虚构点回灌给模型重新生成，最多 `max_correction_attempts = 2` 次 |
| **双向 Fallback** | 规划 / 工具失败时 | 规划失败回退到默认工具列表（`task_fallback`）；工具失败按错误类型换策略或只给已确认信息 |

## 2. 推理模型的坑（实测踩到并已修复）

护栏内部都是"让模型输出 JSON 再解析"的调用。**推理模型会先用 completion token 生成 reasoning_content**，
`max_tokens` 给小了（例如 100 / 300）时预算被推理吃光：`finish_reason=length`、`content` 为空字符串，
JSON 解析必然失败，护栏就**静默退化成"无幻觉 / 在能力范围内"**，等于整层空转。

现在的做法：

1. 结构化判断调用统一按**预算阶梯重试**（幻觉检测 1500 → 3000，边界检查 800 → 1600）；
2. 解析走 `app/agent/json_utils.py::extract_json_object`，容忍代码块包裹、注释、前后解释文字；
3. `HallucinationResult` / `BoundaryResult` 增加 `error` 字段，异常不再静默；
4. 评测脚本单独统计"检测器异常条数"，异常不为 0 时明确提示该指标不可用。

> 经验：用推理模型做结构化判断，要么给足 token 预算，要么换非推理模型；
> "小 max_tokens + 静默兜底"是最危险的组合，会让护栏看起来在工作，实际从未生效。

## 3. 工具错误的统一出口

`tools/errors.py` 统一错误类型（参数错误 / 未找到 / 超时 / 不可用 / 未知工具等），
并区分可重试与不可重试：可重试错误按指数退避重试，不可重试的交给规划节点换策略，
**非幂等写操作（退款）永不重试**。

## 4. 可观测性

每次请求写入 `metadata`，形成可检索的 trace：

| 字段 | 含义 |
|---|---|
| `trace_id` | 本次请求唯一标识 |
| `thread_id` | 会话 / 线程 |
| `selected_agent` | 路由结果 |
| `model_calls` / `tool_calls` | 模型调用次数、工具调用明细 |
| `retry_count` | 工具重试次数 |
| `elapsed_seconds` | 端到端耗时 |

接入 LangSmith 只需配环境变量（`LANGCHAIN_TRACING_V2` / `LANGCHAIN_API_KEY` / `LANGCHAIN_PROJECT`），
未配置时项目正常运行。

## 5. 脱敏

`app/agent/observability.py` 对日志与对外响应脱敏：

- 订单号：保留前缀 + 掩码（`ORD-20240115-001` → `ORD-2024***`）
- 手机号：保留前 3 后 4
- 运单号：保留承运商前缀
- 不记录 API Key，不记录完整敏感个人信息

API 的 `GET /chat/{thread_id}/state` 只返回 `interrupted` / `has_checkpoint` 等脱敏字段，
**不暴露原始 checkpoint 结构**；工具参数与内部思考也绝不返回给用户。
