# 07 · 评估体系与实测结果

对应代码：`app/evaluation/`、`app/scripts/`、`tests/`

## 1. 评估框架：两层 × 两类

| | 代码规则（确定性、零额外成本） | LLM judge（主观质量） |
|---|---|---|
| **过程指标** | 工具准确率、调用效率、token 达标、路由命中 | 过程合理性（工具选择与顺序） |
| **结果指标** | 意图命中、关键信息完整度、转人工判断 | 回答质量（1–5）、事实忠实度（无幻觉） |

约定：某个维度用例里没指定就返回 `None`，聚合时**跳过而不是记 0**，
避免问候类、无工具类用例拉低整体分。

## 2. 沙箱：怎么保证可复现

`app/evaluation/sandbox.py` 做三件事：

1. **隔离**：每条用例独立临时 session 文件；强制关闭记忆读写与 MCP（只用本地 mock 工具）；
2. **插桩**：给共享 client 的 `chat.completions.create` / `beta.parse` 打补丁，
   自动采集每次 LLM 调用的 token、请求的工具、延迟；再包一层 `ToolManager.execute_tool` 采集工具出入参；
3. **执行**：顺序跑完用例的多轮输入，产出 `RunTrace`。

被测对象只有一条主线：`--mode supervisor`（默认）→ LangGraph Supervisor 父图 + 三个子图。

> 评分口径：Supervisor 的路由输出是 `presale` / `postsale` / `complaint`，
> 因此黄金集用 `expected_route` 校验"路由是否正确"；`expected_intent`
> 是早期单 Agent 词表（`order_query` / `product_consult` …）留下的标注，当前不参与评分。

## 3. 数据集

| 数据集 | 文件 | 规模 |
|---|---|---|
| 端到端黄金场景 | `app/evaluation/cases.json` | 10 个完整场景（含多轮、边界、投诉转人工） |
| 意图路由 | `app/evaluation/intent_cases.json` | 100 条（售前 40 / 售后 41 / 投诉 19） |
| RAG 检索 | `app/evaluation/rag_cases.json` | 44 条（编号 22 / 语义 12 / 混合 10） |
| 退款安全 | `tests/test_refund_safety.py` | 10 个专项用例 |
| 事实忠实度 | `app/scripts/run_faithfulness_eval.py` | 81 条问答 + 工具返回 |

## 4. 怎么跑

```bash
python -m app.scripts.run_intent_eval                       # 意图路由准确率
python -m app.scripts.run_rag_eval                          # 标准 vs Adaptive-RAG 检索对比
python -m app.scripts.run_eval --mode supervisor --no-judge # 10 个黄金场景（仅规则指标）
python -m app.scripts.run_eval --mode supervisor            # 带上 LLM judge
python -m app.scripts.run_faithfulness_eval                 # 81 条忠实度 / 幻觉率
pytest                                                      # 全部单元测试（Mock，无需 API Key）
```

## 5. 实测结果

测量环境：LLM `deepseek-flash`（OpenAI 兼容接口）、Embedding `bge-m3` 1024 维、Cohere Rerank 开启。

| 评测项 | 结果 |
|---|---|
| 意图路由 | **93/100 = 93.0%**；售前 36/40（90.0%）、售后 40/41（97.6%）、投诉 17/19（89.5%） |
| RAG 检索（44 条） | 标准 **MRR 0.844** → Adaptive **MRR 0.924**（+10%）；编号类 0.895→0.977、语义类 0.764→0.861、混合类 0.825→0.883 |
| 黄金场景（Supervisor 模式，10 条） | 路由 **10/10**、工具调用准确率 100%、关键信息完整度 100%、转人工判断 100%；通过率 6/10 |
| 单元测试 | **133 passed, 20 skipped**（18 个测试文件） |

**结果解读**

- 黄金场景未通过的 4 条都卡在**效率类指标**：工具调用效率（`min_tool_calls / 实际次数`）和单条用例 token 预算，
  正确性维度（路由、工具命中、完整性、转人工）全部达标——多轮场景会因反复校验而多调几次工具，属于 ReAct 循环的固有代价。
- 检索侧 Precision 会因 RRF 融合更多候选而略降，客服场景更关心"正确文档排得够不够前"（MRR）。

## 6. 边界与注意

- 测试集规模有限（10 / 44 / 81 / 100），结论**只用于版本对比与回归**，不等同线上指标。
- 忠实度评测依赖 LLM judge 输出 JSON：换成推理模型后必须给足 token 预算，
  否则会大量走"检测器异常 → 默认无幻觉"的兜底分支，指标失真（详见 [06-护栏与可观测性](06-护栏与可观测性.md)）。
- 评测命令会真实调用模型，产生费用；日常回归建议先用 `--no-judge` 或 `pytest`。
